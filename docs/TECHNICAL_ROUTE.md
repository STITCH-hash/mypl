# 技术路线说明

## 1. 项目定位

本项目定位为一个基于 Text2SQL 与 RAG 的智能数据问答系统。系统希望让用户通过自然语言查询结构化数据库，并在第二阶段通过 RAG 查询非结构化知识文档，从而提升数据使用效率和知识获取效率。

Text2SQL 是当前第一主线。系统先围绕结构化数据库问答跑通最小闭环，重点解决自然语言问题理解、SQL 生成、SQL 安全校验、数据库执行和结果解释。

RAG 是第二阶段增强模块。它主要用于解释概念、字段口径、业务规则、系统说明和风险提示等非结构化内容，避免把所有知识都硬编码到 prompt 或数据库字段中。

系统本体保持通用化，不绑定某个具体业务场景。初始演示数据集选择股票相关数据，是因为股票数据天然包含基础信息、历史行情、最新行情快照和估值字段，适合演示单表查询、多表关联、聚合统计、时间范围查询和概念解释。股票数据仅用于课程项目演示和数据库问答测试，不提供任何投资建议。

第一阶段数据方案确定为：使用 AkShare 采集约 30 支 A 股股票的基础信息、最近 1 年日行情和一次最新行情快照，清洗后写入本地 SQLite。Text2SQL 只面向 SQLite 生成只读 SQL，不在用户查询时实时调用 AkShare。这样可以保证演示稳定、schema 固定、测试结果可复现。

数据更新策略采用“两步走”：第一阶段手动运行采集脚本，便于调试和准备固定演示数据；第二阶段增加每日 18:00 定时同步任务，更新 SQLite 中的历史日行情和最新行情快照。定时任务应独立于 FastAPI 进程运行，避免后端热重载或多进程部署时重复同步。

课程需求中包含 `select`、`insert`、`delete`、`update` 等数据库操作能力。考虑到大模型生成 SQL 的安全风险，本项目 MVP 阶段先实现只读 `SELECT` 查询；写操作能力仅作为后续受控扩展方向，需要权限控制、人工确认、审计日志和回滚策略之后再考虑。

## 2. 当前采用路线

当前先采用路线 1：纯 Prompt + 大模型 API + 手写 SQL 执行流程。

```text
用户自然语言问题
→ 拼接数据库 schema 与必要约束
→ 调用大模型生成 SQL
→ 后端进行 SQL 安全校验
→ 执行 SQL
→ 返回表格结果
→ 大模型基于查询结果生成自然语言总结
```

这条路线的优点是实现快、依赖低、便于调试、便于在课程报告中解释，也可以作为后续优化的基础。团队可以先把数据库、API、前端页面和大模型调用串起来，再逐步替换或增强其中的模块。

这条路线的不足也比较明确。它对复杂 schema 的支持有限，SQL 生成准确率高度依赖 prompt 质量；缺少 schema 检索和 SQL 示例检索时，面对字段较多或多表关系复杂的问题稳定性不足；同时必须补充 SQL 安全校验机制，避免执行危险语句或超大范围查询。

## 3. 后续演进路线

### 阶段 0：文档和基础设计

- 确定数据库表结构。
- 确定 AkShare 采集范围：约 30 支 A 股、最近 1 年日线、一次最新行情快照。
- 确定股票演示数据库三张核心表：`stocks`、`daily_prices`、`stock_quotes`。
- 确定 API 设计。
- 确定前后端分工。
- 确定测试问题集。

阶段 0 的目标是让团队在动手编码前有共同蓝图。文档不需要一次性完美，但要足够指导第一批开发，避免成员各自实现出不兼容的接口和数据结构。

### 阶段 1：Text2SQL 最小闭环

- 用户输入自然语言问题。
- 使用 AkShare 采集脚本把数据写入 SQLite。
- 第一阶段手动同步数据，第二阶段增加每日 18:00 定时同步。
- 后端读取 schema。
- prompt 拼接 schema 和约束。
- 调用大模型生成 SQL。
- 限制只允许 `SELECT` 查询。
- 执行 SQL。
- 返回结果表格。
- 展示生成 SQL。

阶段 1 是项目最高优先级。只要能够从自然语言问题生成可执行 SQL，并在页面上展示 SQL、表格结果和自然语言摘要，课程项目的核心闭环就已经成立。

### 阶段 2：SQL 安全与稳定性优化

- 禁止 `INSERT`、`UPDATE`、`DELETE`、`DROP`、`ALTER`、`TRUNCATE`、`CREATE` 等危险语句。
- 自动添加 `LIMIT`。
- 检查表名和字段名是否存在。
- 捕获 SQL 执行错误。
- 支持一次错误修复。
- 保存用户问题、SQL、执行结果和错误日志。

阶段 2 的重点是让系统可演示、可复盘、可解释。错误修复可以采用“把数据库错误信息和原始 SQL 反馈给大模型，请它只返回修复后的 SQL”的方式，但仍然要再次执行安全校验。

### 阶段 3：RAG 文档问答

- 支持上传或导入文档。
- 文档切分。
- 向量化存储。
- 检索相关片段。
- 基于检索结果生成回答。
- 展示引用片段。
- 初期可使用 Chroma 作为向量库。Chroma 支持 `PersistentClient` 进行本地持久化存储。

阶段 3 主要解决“数据库查不到但文档能解释”的问题，例如市盈率、ROE、换手率、字段口径、系统使用说明和风险提示。RAG 回答必须展示引用片段，方便用户判断答案来源。

### 阶段 4：Text2SQL + RAG 混合问答

- 数据查询类问题走 Text2SQL。
- 规则解释类问题走 RAG。
- 同时需要数据和解释的问题走混合流程。

示例：

- “过去一个月成交量最高的股票有哪些？”走 Text2SQL。
- “市盈率是什么意思？”走 RAG。
- “为什么某支股票估值偏高？”可以先查指标，再结合知识库解释，但必须提示不构成投资建议。

阶段 4 可以先用简单规则路由，例如根据问题中是否包含“是什么、什么意思、为什么、如何理解”等词判断是否需要 RAG；后续再引入大模型意图分类。

### 阶段 5：可视化和评估

- 使用表格展示查询结果。
- 对适合的数据生成折线图、柱状图。
- 保存测试用例。
- 统计 SQL 执行成功率、SQL 语义正确率、RAG 命中率、平均响应时间等指标。

阶段 5 用于完善课程展示和最终报告。评估不只看能不能运行，还要记录问题类型、生成 SQL、预期结果、实际结果、错误原因和修复情况。

## 4. 推荐技术栈

| 层次 | 推荐技术 | 说明 |
| --- | --- | --- |
| 前端 | Vue 3 + Element Plus + ECharts | Vue 3 适合快速构建交互页面，Element Plus 提供表单、表格和布局组件，ECharts 方便展示折线图、柱状图等数据图表。 |
| 后端 | FastAPI | FastAPI 与 Python 大模型生态集成自然，接口声明清晰，自动生成 OpenAPI 文档，适合课程项目快速开发。 |
| ORM / 数据库访问 | SQLAlchemy 或直接 SQL 执行封装 | SQLAlchemy 是 Python 常用 SQL 工具和 ORM；初版也可以使用轻量封装直接执行只读 SQL，降低复杂度。 |
| 数据库 | 开发阶段 SQLite，展示阶段可切换 MySQL | SQLite 便于本地开发和演示，MySQL 更接近常见课程项目部署环境。 |
| 数据来源 | AkShare + pandas | AkShare 用于采集股票基础信息、历史日行情和最新行情快照，pandas 用于字段清洗和写入 SQLite；相关依赖可放在单独的数据采集 requirements 中，避免影响后端最小启动。 |
| 向量库 | Chroma | Chroma 适合本地向量库持久化，RAG 阶段可使用 `PersistentClient` 保存知识库向量。 |
| 大模型 | 统一封装 `LLMClient` | 业务代码不写死在某一家模型 API 上，便于替换模型、统一错误处理和记录调用日志。 |
| 版本控制 | Git | 用分支、提交和 PR 管理团队协作，避免最后集中改动难以追踪。 |

## 5. 系统模块划分

### 1. 前端问答模块

负责提供用户自然语言输入框、提交按钮、历史问答展示和加载状态。它需要同时展示用户问题、生成 SQL、查询结果表格、自然语言总结和错误提示。

### 2. 后端 API 模块

负责对外提供统一 HTTP 接口，例如 Text2SQL 查询、schema 查询、RAG 查询、混合问答和评估接口。该模块应保持请求体和响应体稳定，方便前后端并行开发。

### 3. 数据库连接模块

负责读取数据库配置、建立连接、管理连接生命周期和执行基础健康检查。开发阶段可以优先支持 SQLite，展示阶段再扩展 MySQL。

### 3.1 AkShare 数据采集模块

负责封装 AkShare 调用和数据同步脚本。第一阶段只采集 `stocks`、`daily_prices`、`stock_quotes` 所需字段，并把中文字段统一清洗成适合 SQL 和大模型理解的英文字段名。

### 3.2 定时同步模块

负责每天 18:00 触发一次 AkShare 数据同步，更新本地 SQLite 演示库。该模块建议以独立脚本运行，不放在 FastAPI 主进程中，避免开发环境热重载造成重复任务。

### 4. Schema 读取模块

负责读取数据库中的表名、字段名、字段类型、主键、外键和字段说明。Text2SQL prompt 依赖该模块提供准确、简洁的 schema 信息。

### 5. Prompt 构造模块

负责把用户问题、数据库 schema、SQL 生成规则和安全约束拼接成大模型输入。该模块需要明确要求模型只输出 SQL 或指定 JSON 格式，减少后处理难度。

### 6. Text2SQL 生成模块

负责调用 `LLMClient`，将自然语言问题转换为 SQL。它应记录原始问题、模型响应、解析后的 SQL 和调用耗时，方便评估和排错。

### 7. SQL 安全校验模块

负责在执行前检查 SQL 是否只包含允许的只读查询。它需要拦截危险关键字、限制多语句执行、检查表名字段名，并为没有限制的查询自动补充 `LIMIT`。

### 8. SQL 执行模块

负责执行通过安全校验的 SQL，并将数据库结果转换为统一的 `columns` 和 `rows` 格式。它还需要捕获数据库异常，返回可读错误信息，而不是让后端服务崩溃。

### 9. 查询结果解释模块

负责把 SQL 查询结果、字段含义和用户原问题交给大模型生成简洁总结。总结应忠实于查询结果，不得编造数据库没有返回的信息。

### 10. RAG 文档管理模块

负责导入、解析、分类和更新知识库文档。初期可支持 Markdown、TXT 和 PDF，后续再扩展 DOCX、PPTX 等格式。

### 11. 向量检索模块

负责把文档切片向量化并写入 Chroma，查询时返回相关片段和来源信息。检索结果要保留文档名、片段内容和相似度，便于前端展示引用。

### 12. 混合问答路由模块

负责判断用户问题应该走 Text2SQL、RAG 还是混合流程。初期可以用规则判断，后续可以用大模型做意图分类。

### 13. 测试评估模块

负责维护测试问题集、预期 SQL 或预期结果、实际执行结果和评估指标。评估指标包括 SQL 执行成功率、SQL 语义正确率、RAG 命中率和平均响应时间。

### 14. 日志模块

负责记录用户问题、生成 SQL、执行状态、错误信息、RAG 命中文档和接口耗时。日志中不得记录 API Key 或其他密钥，必要时对用户输入做脱敏处理。
